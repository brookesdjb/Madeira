# FEX translation and execution investigation

Snapshot and evidence classifications: [architecture](architecture.md). Recommendations use stable IDs from [the backlog](recommendations.md). No hardware measurements were made here.

## Trace: guest entry to ARM64 execution

1. Wine's ARM64EC machinery enters `xtajit64`; its per-thread initialization calls `CTX->CreateThread(0,0)` and associates the state with the thread CPU area. [FEX/Source/Windows/ARM64EC/Module.cpp:1754–1820](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/Source/Windows/ARM64EC/Module.cpp#L1754-L1820). The WoW64 module is a separate translator entry path (`FEX/Source/Windows/WOW64/Module.cpp`), with guest-window address translation. They do not use the app harness's one global test thread.
2. `ContextImpl::CreateThread` sets up the frontend decoder, opcode dispatcher, pass manager, register allocation and backend for that thread: [FEX/FEXCore/Source/Interface/Core/Core.cpp:480–531](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/Core.cpp#L480-L531). Guest integer/vector state is held in a CPU state frame and statically allocated host registers where possible.
3. Emitted dispatcher code probes L1 first on this port, then L2 when enabled, and spills/re-enters C++ on a miss. The iOS L1-first path is already an important correction for high guest addresses: [FEX/FEXCore/Source/Interface/Core/Dispatcher/Dispatcher.cpp:260–348](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/Dispatcher/Dispatcher.cpp#L260-L348). The historical cost described in comments predates the fix and is not current measured overhead.
4. `ContextImpl::CompileBlock` canonicalizes/validates Madeira aliases and takes a shared invalidation lock, then asks `LookupCache::FindBlock`; a C++ lookup hit is **not** a compilation. [FEX/FEXCore/Source/Interface/Core/Core.cpp:2118–2168](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/Core.cpp#L2118-L2168). `FindBlock` has lock-free thread-local L1, followed by a shared-map read lock for L2/L3: [FEX/FEXCore/Source/Interface/Core/LookupCache.h:200–248](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/LookupCache.h#L200-L248). Generated fast paths and C++ fallback counts must be measured separately.
5. A real miss decodes guest instructions, builds multiblock IR, dispatches opcodes and runs passes. [FEX/FEXCore/Source/Interface/Core/Core.cpp:857–940](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/Core.cpp#L857-L940), [FEX/FEXCore/Source/Interface/Core/Core.cpp:1174–1243](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/Core.cpp#L1174-L1243). Default optimization passes include x87 stack optimization and redundant/dead flag calculation elimination, followed by register allocation. [FEX/FEXCore/Source/Interface/IR/PassManager.cpp:87–114](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/IR/PassManager.cpp#L87-L114). Diagnostic topology sweeps are opt-in. Do not use `FEX_O0` as a production fix for a suspected pass issue.
6. ARM64 code is emitted into a **private temporary buffer before** the shared code-buffer publication lock. [FEX/FEXCore/Source/Interface/Core/JIT/JIT.cpp:985–1013](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/JIT/JIT.cpp#L985-L1013). The publication phase locks `CodeBufferWriteMutex`, checks generation changes, copies/fixes up code and updates the shared buffer: [FEX/FEXCore/Source/Interface/Core/JIT/JIT.cpp:1240–1385](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/JIT/JIT.cpp#L1240-L1385). Moving all emission under this lock would regress concurrency.
7. Code publication performs instruction-cache synchronization. For Windows-on-iOS, the path calls `NtFlushInstructionCache`; the port comments document stale cross-core instruction execution when it used only inline maintenance. [FEX/FEXCore/Source/Interface/Core/JIT/JIT.cpp:18–32](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/JIT/JIT.cpp#L18-L32), [FEX/FEXCore/Source/Interface/Core/JIT/JIT.cpp:1397–1423](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/JIT/JIT.cpp#L1397-L1423). Keep this invariant even if batching publications is investigated.
8. Block mappings/ranges are published and the dispatcher jumps into ARM64 code. Direct branches can be linked/backpatched; indirect exits probe L1 and fall back to dispatch. [FEX/FEXCore/Source/Interface/Core/JIT/BranchOps.cpp:46–104](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/JIT/BranchOps.cpp#L46-L104), [FEX/FEXCore/Source/Interface/Core/JIT/BranchOps.cpp:240–378](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/JIT/BranchOps.cpp#L240-L378). Native ARM64EC exits save guest state and follow ABI/FP-state rules; they are not ordinary same-ABI C calls.

Unsupported opcode handling can terminate/split IR generation; scalar/x87 helper fallback routines are also present (`Interface/Core/Interpreter/InterpreterOps.h`, dispatcher helper tables). This does **not** establish a general interpreter silently running an entire slow game. Attribute sampled fallback addresses before proposing an interpreter optimization.

## Translation granularity and sharing

Defaults in [FEX/FEXCore/Source/Interface/Config/Config.json.in:1–40](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Config/Config.json.in#L1-L40) are multiblock on and maximum 5,000 guest instructions, with code caching WIP off. This is an upper bound, not a promise that every region contains 5,000 instructions. Branch structure, decoding errors, traps and configuration change the result. Larger regions reduce dispatch opportunities but cost more decode/IR time and may produce cold code. Proposed **F2** uses per-game diagnostic experiments, not a global smaller-block default.

Two threads can race to generate the same IR. `CompileCode` rechecks the map and discards its IR if another thread won; comments explicitly describe trading duplicate work against lock contention. **F3** is to instrument duplicate work first. A per-RIP compile-in-progress mechanism must allow recursive exception/delivery paths to bypass waiting; an unconditional promise/future can deadlock a compiler interrupted by an exception.

Lookup caches are per thread, but compiled-code maps are attached to shared code buffers. L1-only mode already exists; it saves the L2 table/arena but raises miss/fallback risk. Allocation bytes are virtual allocation sizes, not equal to resident dirty footprint. iOS zero-scrubbing reads and only clears stale pages rather than dirtying the full region: [FEX/FEXCore/Source/Interface/Core/LookupCache.cpp:33–158](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/LookupCache.cpp#L33-L158). A lower RSS with L2 disabled does not prove improved frame times.

Code buffers start at 16 MiB and can reach 128 MiB; iOS rollover has special allocation/reclamation rules: [FEX/FEXCore/Source/Interface/Core/CPUBackend.cpp:20–38](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/CPUBackend.cpp#L20-L38), [FEX/FEXCore/Source/Interface/Core/CPUBackend.cpp:508–552](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/CPUBackend.cpp#L508-L552), [FEX/FEXCore/Source/Interface/Core/CPUBackend.cpp:625–672](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/CPUBackend.cpp#L625-L672). Do not confuse these buffers with the app bridge's nominal 64 MiB harness pool. The Wine allocator has pool-head PE copies and tail JIT allocations, freelists and ledgers (`build/ntdll-unix/virtual_ios.c:184–215,2307–2697`). Increasing pool size blindly can exchange compilation churn for memory pressure.

## Ordering, atomics and exceptions

x86 ordering has a real instruction cost. The load/store TSO emitters select LDAPR/LDAR or LDAPUR and STLR/STLUR according to host features; vector/atomic paths use barriers when required. [FEX/FEXCore/Source/Interface/Core/JIT/MemoryOps.cpp:899–1008](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/JIT/MemoryOps.cpp#L899-L1008), [FEX/FEXCore/Source/Interface/Core/JIT/MemoryOps.cpp:2063–2128](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/FEXCore/Source/Interface/Core/JIT/MemoryOps.cpp#L2063-L2128). Atomic emitters (`JIT/AtomicOps.cpp`) and unaligned handlers (`Utils/ArchHelpers/Arm64.cpp`) are separate paths. Cache-line/page-split atomics need special correctness handling; tests already exercise strict split-lock behavior. Turning off TSO, strict split locks, or vector ordering is not an acceptable generic speedup.

Host probing occurs in native `madeira_publish_host_probe`, which exports sysctl results to the PE translator: [app/Madeira/WineProcessBridge.m:797–835](https://github.com/willfaust/Madeira/blob/48f976429c189f8396e23d251d8a82f43c705922/app/Madeira/WineProcessBridge.m#L797-L835). ARM64EC enables LRCPC2 only on an explicit supported result and defaults AFP off to avoid repeated FPCR transitions: [FEX/Source/Windows/Common/CPUFeatures.cpp:136–164](https://github.com/willfaust/FEX/blob/3bec2ac498bf78156ab47c0c194b0e8cb2849756/Source/Windows/Common/CPUFeatures.cpp#L136-L164). Both are **already implemented**. FEX's newer instruction forms require the port's fault decoders to understand them too. Unknown optional features remain an audit concern; do not force features based merely on an “M-series” label. AVX/AVX2 is an explicit compatibility option implemented through 128-bit paths, not evidence of host SVE.

Memory protection, write tracking and self-modifying code trigger invalidation through `Source/Windows/Common/InvalidationTracker.cpp` (especially `HandleSMC`, around 508). This interacts with Wine's Mach exception handler and alias bookkeeping, not Linux signal behavior. Shared invalidation locks coordinate compilation; synchronous exception delivery has an unpublished one-shot compile path specifically to avoid re-entering locks held by the interrupted thread. Its bounded spin/failure behavior must be preserved. Page-fault count by cause is more useful than treating all exceptions as translator misses.

JIT executable pages require the app's debugger-enabled mechanism and RW/RX mappings (`app/Madeira/JITAllocator.c`, `FEXBridge.mm`, `build/ntdll-unix/virtual_ios.c`). Written bytes and executable aliases are different addresses; canonical guest addresses, unwind metadata, block link addresses and exception PC reconstruction must agree. Removing alias flushes or mapping executable guest pages indiscriminately risks correctness and JIT functionality.

## Actual concurrency and limits

**Yes: multiple guest threads execute translated ARM64 code simultaneously.** Each Wine pthread gets a FEX thread/frame, and compiled execution does not take one global interpreter lock. Per-thread decoder/pass/emitter state permits concurrent compilation preparation. Shared code emission/publication, invalidation, mapping and allocator paths can still serialize bursts. This conclusion is a code trace, not a measured M-series scaling curve.

During warm gameplay, measure guest workers' CPU time and runnable/waiting state separately from compile workers. Low utilization could mean synchronization latency, GPU waits or frame caps, not FEX single-threading. More exposed guest CPUs can also create more compiler caches, Wine stacks and shader workers, raising footprint and scheduler contention.

## Can translated code persist across launches?

Technically possible as **cache data**, but not demonstrated by this integration. FEX already contains `CodeCache::LoadCache`, relocation machinery and `EnableLoadedSection` (`Core/CodeCache.cpp:558–640,640–892`); defaults mark this WIP and off. This is not proof that Madeira can load that representation through its iOS pool.

A viable implementation must key on executable content, FEX build/IR ABI, guest mode, host features, ordering/FP options and relevant compatibility settings. It must relocate guest bases, runtime helpers, link records and RW/RX offsets; rebuild metadata and invalidate on changed guest code. Never persist raw TEB/frame/native object pointers. Load validated data into currently authorized executable memory, publish with the existing cross-core cache protocol, and fall back to fresh compilation on any mismatch. Disk caching does **not** remove debugger/JIT authorization or code-signing requirements. A block-offset hot-set cache that prewarms using the normal compiler is a lower-risk first step, but could still contend with loading/rendering and increase startup work.
